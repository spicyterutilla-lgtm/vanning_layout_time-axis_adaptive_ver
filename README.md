# 4D Vanning Optimization System（時間軸適応型 バンニング最適化システム）

本プロジェクトは、コンテナの積載効率（充填率）を最大化するための **「4D（3D空間 + 時間軸）最適化システム」** です。
従来の静的な3Dパズル（空間のみの最適化）に「時間軸（Time Axis）」の概念を加え、未来の荷物を前倒し（Pull）したり、現在の荷物を繰り越し（Push）することで、コンテナの充填率を限界まで高めることを目的としています。

Excelの貨物リストをブラウザにアップロードすると、3Dパッキング計算・時間軸操作・出荷判断を自動で行い、結果をWeb画面で可視化し、バンニング指示書（Excel）として出力できます。

## 背景と課題（いすゞロジスティクス様のケース）

物流現場において、以下の厳しい制約が存在します。
*   **【KPI】充填率80%の壁**: コンテナの積載率（体積）が80%未満の場合は赤字となる。
*   **納期絶対**: 船での輸送に1〜2ヶ月かかるため、現地の工場への納期は絶対条件。
*   **保管期限の限界**: 木箱などの梱包材には耐久性（防錆等）の限界があり、倉庫内での保管・前倒し待機は「最大3週間（21日）」。
*   **倉庫キャパシティ**: 保留プール（繰り越し荷物）を無制限に置くことはできない。

## システムの特長（Paradigm Shift）

これらの課題を解決するため、本システムは以下の機能を備えています。

1.  **時間軸操作アルゴリズム（Pull & Push）**
    *   **前倒し（Pull）**: コンテナ体積充填率が80%未満の場合、納入済みの「前倒し可能」な荷物を引っ張ってきて80%以上を達成します。
    *   **繰り越し（Push / 待機）**: 納期に余裕がある場合（全荷物が翌週以降まで待機可能な場合）、無理に出荷せず「保留プール」に入れ、次回の荷物と合流させて再計算し、高充填率を目指します。
2.  **ステータスの可視化**
    *   🟢 **正常クリア**: 体積充填率80%以上
    *   🔵 **前倒し補填 / 繰り越し合流**: 時間軸操作によって赤字を回避したコンテナ
    *   🔴 **納期優先の赤字出荷**: 前倒しも繰り越しもできず、納期・木箱期限の限界のため赤字覚悟で強制出荷するコンテナ
3.  **高速な3Dパッキング計算**
    *   Numbaで機械語コンパイルしたGuillotine Split法（`numba_packing.py`）により、3D配置の当たり判定・空間分割をC言語相当の速度で実行します。
    *   複数のソート戦略を比較し、最も良い初期配置を選択。さらに局所探索（統合・救済・再パッキング）で赤字コンテナを削減します。
    *   `deep` モードでは遺伝的アルゴリズム（GA）で積載順序そのものを最適化します。

## 技術スタック

*   **バックエンド**: Python 3.12（3.10以上を想定）, Flask
*   **最適化アルゴリズム**: Numba（JITコンパイル）, 独自メタヒューリスティクス・エンジン（`metaheuristics_engine.py`, `vanning_engine.py`, `numba_packing.py`）
*   **データ処理**: pandas, numpy, openpyxl
*   **フロントエンド**: HTML, CSS, Vanilla JavaScript（フレームワーク非依存）

## 動作環境

*   **Python**: 3.12.4 で動作確認済み（3.10以上を推奨）
*   **OS**: Windows 11 で動作確認済み（Flaskのため macOS / Linux でも動作可能）
*   **メモリ**: 数百〜千件規模の計算のため 4GB 以上を推奨
*   依存ライブラリは `requirements.txt` を参照。

> **補足（バージョンの組み合わせ）**: 起動時に `A NumPy version ... is required for this version of SciPy` という警告が出ることがあります。これは numba が間接的に参照する SciPy と新しい numpy の組み合わせによる警告で、本システムの動作には影響しません。気になる場合は `numpy<2.3` で揃えてください。

## セットアップと起動方法

### 1. 必要なライブラリのインストール

```bash
pip install -r requirements.txt
```

### 2. アプリケーションの起動

```bash
python app.py
```

デフォルトで `http://127.0.0.1:5000` でサーバーが起動します。ブラウザでアクセスしてGUIを利用できます。
同一ネットワーク内の別PCからは `http://<起動PCのIPアドレス>:5000` でアクセスできます（`host='0.0.0.0'` で待ち受けているため）。


## 使い方（操作の流れ）

ブラウザ画面（または API）で、以下のステップで利用します。

1.  **サンプルデータの取得（任意）**
    手元に貨物リストが無い場合、本リポジトリの `simulationdata/` フォルダ内にあるパターンA〜CのExcelデータをテスト用にお使いいただけます。
2.  **Excelのアップロード**
    貨物リストのExcel（`.xlsx` / `.xls`）をアップロードします。列名は日本語/英語のゆらぎを吸収して自動マッピングされます（例: 「L」「長さ」「Length」はすべて長さとして認識）。ヘッダー行も自動検出します。
    *   **必須列**: 品名（資材名称）、L（長さ）、W（幅）、H（高さ）
    *   **任意列**: 重量、納入予定日、バンニング完了期限、木箱期限、仕向け地、各種コード、優先度、強制出荷 など（未入力の列は補完値で計算され、画面に「準備度」として明示されます）
3.  **基準日の設定と最適化の実行**
    作業基準日（情報受領日）を指定して最適化を実行します。基準日から船積日までの **21日間** が積込対象ウィンドウになります。
4.  **結果の確認**
    コンテナごとの体積/重量充填率、3D配置（Three.js等による可視化）、出荷判断（🔴🔵🟢）、時間軸操作のログを確認できます。
5.  **手動調整（任意）**
    特定コンテナを編集モードにし、荷物の追加・削除・並べ替えが可能です。3D再配置・重量超過判定が即時に行われ、Undo / Redo / 編集前への復元に対応します。
6.  **指示書の出力**
    全コンテナ分のバンニング指示書（Excel）、または単一コンテナ分のExcelを出力します。納品順サマリー・最適化評価・前提サマリー・実務準備度の各シートが付きます。

## 検証用データ（simulationdata）について

システムの動作検証・パターンテスト用に、`simulationdata/` フォルダ内に3種類のExcelデータを用意しています。用途に合わせてアップロードしてお試しください。

*   **パターン A（通常規模 / 800件）**
    *   **ファイル**: `A_case_master_based_simulation_data.xlsx`
    *   **内容**: 1週間あたりの標準的な物量。現場の安全基準（底面接地率100%等）を満たす計画が、どれだけの実用速度で自動生成されるか（ベースライン確認）を検証するためのデータです。
*   **パターン B（少なめ / 500件）**
    *   **ファイル**: `B_case_master_based_simulation_data.xlsx`
    *   **内容**: そのまま積むとコンテナがスカスカ（空気を運ぶ状態）になるケース。未来の荷物をパズルのピースとして前倒し（Pull）で引き当てられるかを検証します。
*   **パターン C（多め / 1,200件）**
    *   **ファイル**: `C_case_master_based_simulation_data.xlsx`
    *   **内容**: 荷物が大量に滞留したケース。計算量が爆発する膨大なデータでも、フリーズせず実用時間内に処理を完了できるか（堅牢性の証明）を検証します。

## 最適化モード（fast / deep）

最適化実行時に2つのモードを選べます。

| モード | 内容 | 計算時間の目安 |
| --- | --- | --- |
| **fast**（既定） | 複数のソート戦略を比較して最良の初期配置を選び、局所探索（低充填コンテナの統合・救済・ペア再パッキング）で赤字を削減します。 | 数秒〜十数秒 |
| **deep** | fastの結果をエリート初期解として遺伝的アルゴリズム（GA）に渡し、積載順序を最適化します。より多くの荷物を80%以上で積み切れる場合があります。 | 約60秒（`time_limit_seconds` で固定） |

> 参考: 120件のサンプル（必須110件）での実測では、fast=4本（57件積載・約11秒）、deep=6本（90件積載・約60秒）。deepはより多くの荷物を当週で積み切る解を見つけられる場合があります。いずれのモードでも3D配置の幾何検証（はみ出し・重なり・宙づき・上載せ重量逆転）はパスします。

## 積載制約のルール

3Dパッキングは以下の制約を厳守します（ソースコード実装準拠）。

*   **完全収容**: すべての箱はコンテナの有効内寸（`12000 × 2300 × 2400 mm` = 66.24 m³）に完全に収まる。
*   **平行配置・重なり禁止**: 箱は座標軸に平行に置き、互いに交差しない。
*   **向き**: 天地は固定（高さは不変）。水平方向の90°回転（L↔W入れ替え）のみ許可。
*   **最大重量**: 1コンテナ 22,000 kg 以下。
*   **接地・安定性**: 床に直接置くか、単一の箱の上に載せる（跨ぎ・宙づき禁止）。上の箱の底面は下の箱の上面に100%収まり、上が下より重くならない。
*   **重心**: 水平方向の重心が床面中心から半径300mm以内。
*   **配送先順**: 仕向け地を考慮し、遠い配送先ほど奥（X奥）に配置（荷下ろし順）。

| メソッド | パス | 用途 |

## 本番運用・納品時の注意

現状の `app.py` は **開発サーバ設定** です。社内ツールとしてローカルで使う分には問題ありませんが、本番・共有環境へ展開する場合は以下を検討してください。

*   **デバッグモード**: `app.run(debug=True, ...)` は例外時にWerkzeugデバッガ（任意コード実行が可能）を公開します。共有環境では `debug=False` にしてください。
*   **待ち受けアドレス**: `host='0.0.0.0'` は同一ネットワークの他端末からアクセス可能です。LAN内に閉じる前提でファイアウォール等を確認してください。
*   **セッション状態**: セッションはサーバプロセス内の単一のグローバル辞書（`services/session.py`）で保持します。**複数ユーザーが同時利用すると状態を共有・上書きします**。単一ユーザー／単一タブでの利用を前提としてください。
*   **WSGIサーバ**: 常時稼働させる場合は Flask開発サーバではなく、waitress / gunicorn 等のWSGIサーバ経由での起動を推奨します。
