時間軸対応バンニングレイアウトシステムの入力データ設計と日次シミュレーション運用
エグゼクティブサマリー
高品質なバンニングレイアウトシステムを作るうえで、最初に変えるべき発想は、入力を「今日積む荷物リスト」にしないことです。現場オペレーター視点では、毎日扱うべきデータは「今ある在庫」だけでも「未来予定」だけでもなく、時刻情報を持つ荷物プールです。その上で、当日になったら available_date・due_date・storage_deadline・force_ship・priority を使って「今日絶対出すもの」「今日出してもよいもの」「まだ出せないもの」を分類し、その選ばれた候補集合だけを 3D パッキングへ渡す、という二段構えが最も実務的です。これは、あなたが共有したメモの「時間付きの荷物プール」という考え方と一致しており、rolling horizon planning の文献が示す「毎期、最新情報で再計画しつつ、直近の決定だけを確定する」やり方とも整合します。 
また、業務ロジックと幾何パッキングを分けることが重要です。先に「何を今日出すか」を決め、その後で packing_3d.py のような 3D エンジンに「どう積むか」を解かせる構成にすると、納期・保管期限・前倒し・優先度のような時間軸判断と、安定性・支持面・重心・空き空間といったレイアウト品質を同時に扱いやすくなります。近年の実務志向 3D-BPP 研究でも、重量制約、荷重バランス、安定性、非積載属性、順序制約、負荷分散などを別々の制約として持たせるのが一般的です。
コンテナ寸法は、公開されている一般的な 40ft HC の内寸ではなく、現場が示した「ケースが置けるスペース」＝ usable envelope をハードリミットに採用するのが正しいです。ISO 668 はコンテナの標準的な外寸・内寸・ドア開口を規定していますが、実務上の搭載可能空間はローカル運用、余裕、緩衝材、作業安全マージンによって、それより小さく置かれることがあります。したがって、今回のシステムでは usable_L=12000, usable_W=2300, usable_H=2400 をパッキング判定に使い、必要があれば参考値として physical_* を別保持する設計が最も安全です。usable volume は 66.24 m³ です。
重量については、いまの前提をそのまま乱数化すると破綻しやすい点に注意が必要です。もしコンテナ上限が 22,000 kg なら、8 ケース積載時の平均重量は 2,750 kg/ケース以下、40 ケース積載時は 550 kg/ケース以下でなければなりません。したがって、「各ケースを一律に 1,000–15,000 kg からランダム生成する」方式では、40 ケース近い高密度シナリオは再現できません。このため、実装では「厳しい重量ストレス試験用データ」と「レイアウト密度試験用データ」を分けるか、少なくともケース種別ごとの weight class と分布を持つべきです。
最後に、KPI は一つの総合点よりも、体積充填率・重量充填率・重心位置・高重心警告・前後偏荷重警告・未積載件数・空き体積分布のような分解可能な指標で出す方が、現場にも開発側にも使いやすいです。重心については、左右方向をいきなり hard constraint にする必要はありませんが、x/y/z の 3 軸で必ず計算して可視化はするべきです。重量バランス、安定性、支持制約、重心の移動は、近年の現実的な packing 研究でも重要な品質指標として扱われています。
前提条件と設計原則
高品質なバンニングシステムの入力設計は、単なる「箱寸法の一覧」では足りません。実務志向の 3D bin packing 研究では、対象データに少なくとも 寸法、重量制約、安定性、順序の優先、カテゴリ親和性、負荷分散、荷重バランスが必要であることが繰り返し示されています。さらに、online / rolling horizon の文脈では、全アイテムが最初から確定しているとは限らず、「何個先まで見えているか」がアルゴリズムの挙動を大きく左右します。したがって、現場運用向けの設計原則は、静的な一括積みではなく、見えている未来を活用する日次再計画です。
この観点から、入力データは次の三層に分けて考えるのが最も明快です。第一に、ケースそのものの形状・回転可否・積み上げ可否などを持つケースマスタ。第二に、個体ごとの利用可能日、納期、保管期限、重量、優先度を持つ荷物台帳。第三に、いつどのコンテナ枠が使えるかを持つコンテナ出荷枠です。実際のシミュレーションはこの三層を参照し、当日ごとに available / must_ship / optional / future / forwardable を判定して進みます。これは、あなたが共有した「今日の荷物一覧ではなく時刻付きの候補プール」という整理と一致しています。
今回の案件では、container physical dimensions と usable envelope を明確に分けるべきです。ISO 668 の文脈では標準コンテナには内寸・ドア開口・定格が定義されていますが、実務系 packing エンジンでは、計算上の bin dimensions を「現場で安全に使える空間」に下げて扱う設計がよく採られます。あなたが提示した図面値はまさにその usable envelope なので、packing_3d.py の判定、体積計算、3D 描画枠、KPI の母数をすべて L=12000, W=2300, H=2400 に統一するのが最優先です。
さらに、選択問題と配置問題は分けて実装した方がよいです。vanning_engine.py は本来「今日どの荷物を対象にするか」を決める層、packing_3d.py は「決まった候補をどう置くか」を解く層、models.py は両者で使う item/container/setting の契約を定義する層、と役割を分けると、時間軸ロジックを強化しても 3D エンジンをほぼそのまま再利用できます。実務向け packing 研究でも、重量制約や支持制約を満たす配置生成は、Extreme Points や候補点探索に任せ、その前段で item ordering や due-date logic を与える構成が主流です。
入力データスキーマ
物理的な保存形式としては、item_schedule を唯一の真実の表にし、current_inventory と future_schedule はそこから日次に切り出す view として扱うのが最も安全です。ただし、現場説明や Excel テンプレートの理解を優先するなら、概念上は「ケースマスタ」「現在在庫」「未来予定」「コンテナ枠」「設定値」の 5 スキーマで説明するのがわかりやすいです。これは、あなたの現在の設計メモや、現実の 3D packing ベンチマークが item/bin dimensions, weight restrictions, ordering preferences, load balancing といった複数の情報層を分けて持つ考え方とも整合します。

日次分類とルックアヘッド
日次シミュレーションの分類ルールは、available を母集合とし、その中を must-ship / optional に分け、future は別集合、forwardable は optional の部分集合にするのが扱いやすいです。「今日出せるかどうか」と「今日出すべきかどうか」を分けると、業務ロジックが非常に明快になります。これは、rolling horizon の myopia 回避と、online packing の limited visibility の両方に整合する考え方です。 
class	判定ルール	意味	今日の扱い
available	available_date <= plan_date and status in {stock, ready}	物理的に今日積める	対象候補
must_ship	available and (force_ship=1 or min(due_date, storage_deadline) <= plan_date)	今日出さないと危険	最優先で選択
optional	available and not must_ship	今日でも後日でもよい	充填率補完候補
future	available_date > plan_date	まだ現場にない / 積めない	予見には使うが本日積まない
forwardable	optional and allow_early_ship=1 and schedule_class in {'firm','tentative'}	前倒ししてもよい	低充填救済用に追加
ここで重要なのは、forwardable は future ではなく available の部分集合だという点です。つまり「納期は先だが、もう現場に来ているもの」だけが前倒し候補です。まだ現場に来ていない荷物を today’s packing target にしてしまうと、時間軸シミュレーションではなく願望計画になってしまいます。
優先順位は、選択優先と配置優先を分けて定義するのがよいです。選択優先は業務判断で、基本は force_ship、must_ship_date=min(due_date, storage_deadline)、priority、age_days=plan_date-available_date を使います。配置優先は幾何判断で、stackable、footprint_area、height、weight_kg、must_ship_date を使います。研究でも、packing 処理には安定性や支持・重量分布の制約が重要であり、さらに due dates や loading/unloading order は別の高次制約として効いてきます。

ルックアヘッドは、2週間・1か月・2か月を用途別に切り分けるのが現実的です。rolling horizon 研究では、長い horizon は myopia を減らす一方、遠い将来ほど forecast error の影響も受けやすく、実際には「毎回再計画し、直近決定のみ固定する」設計が推奨されます。したがって、lookahead_days は「何日先まで見えるか」と「その先の情報をどの程度信じるか」を分けて設定すべきです。

lookahead_days の実務的な決め方
text
コピーする
lookahead_days = min(visible_total_days, max(max_storage_days + avg_dispatch_interval_days, 14))
この式で、max_storage_days=21、平均出荷間隔が週1回相当なら 21+7=28 なので、初期値は 30 日がもっとも扱いやすいです。日次運用では 30 日を見つつ、forwardable として実際に使うのは 14–30 日以内の firm / tentative に限る、という運用が妥当です。
重量の扱いは、ケース種別ごとの class-based estimation を基本とし、actual weight が入ったら必ず上書きする構成がよいです。理由は単純で、1,000–15,000 kg を一律ランダムに振ると、コンテナ最大重量 22,000 kg に対して高密度ケース数が再現できないからです。8 ケース積みなら平均 2,750 kg/ケース以下、40 ケース積みなら平均 550 kg/ケース以下である必要があるため、1,000 kg を最小に固定したまま 40 ケースを載せることは不可能です。したがって、重量テストは「geometry density test」と「heavy CG stress test」に分けるべきです。

ローリングシミュレーション
rolling simulation は、2か月分を一度に固定最適化するのではなく、毎日、その日までに available なものだけで意思決定し、未来は参照だけして明日に持ち越すやり方が基本です。最新の需要情報で再計画し続ける rolling horizon の利点は、短期予測の改善を毎期取り込みつつ、先の期間に対する過度なコミットを避けられる点にあります。あなたが共有したメモの「今日の判断だけを確定し、翌日また最新データで判断し直す」という考え方は、この rolling horizon の定石そのものです。 
日次のオペレーションに落とすと、処理順はこうなります。朝時点で在庫と未来予定を読み込み、plan_date を基準に分類し、must-ship を先に確保し、空きが多い枠だけ optional / forwardable で補完し、3D packing を走らせ、KPI を見ながら確定し、ship された item を ledger 上で shipped に更新する。この流れだと、「期限切れを起こさない」「今日の出荷枠をスカスカのまま終えない」「未来の逼迫も見ながら動く」を同時に満たせます。

def run_rolling_sim(item_ledger, container_slots, settings):
    results = []

    for plan_date in daterange(settings.plan_start_date, settings.plan_end_date):
        todays_slots = container_slots[
            (container_slots.ship_date == plan_date) &
            (container_slots.status == "planned")
        ]

        visible = item_ledger[
            (item_ledger.status.isin(["stock", "ready", "future"])) &
            (item_ledger.available_date <= plan_date + days(settings.lookahead_days))
        ]

        available = visible[
            (visible.available_date <= plan_date) &
            (visible.status.isin(["stock", "ready"]))
        ]

        must_ship = available[
            (available.force_ship == True) |
            (min_date(available.due_date, available.storage_deadline) <= plan_date)
        ]

        optional = available.drop(must_ship.index)

        forwardable = optional[
            (optional.allow_early_ship == True) &
            (optional.schedule_class.isin(["firm", "tentative"]))
        ]

        must_ship = sort_for_selection(must_ship)
        optional = sort_for_selection(optional)
        forwardable = sort_for_selection(forwardable)

        day_ship_list = []
        unresolved = []

        # まず must_ship を枠へ入れる
        for slot in todays_slots:
            selected = take_items_for_slot(must_ship, slot)
            pack_result = pack_3d(selected, slot.usable_dims, slot.max_weight)
            day_ship_list.append(pack_result)
            must_ship = must_ship.remove(pack_result.packed_ids)
            unresolved.extend(pack_result.unpacked_items)

        # 低充填コンテナを forwardable で救済
        for pack_result in day_ship_list:
            if pack_result.fill_rate_volume_pct < settings.min_fill_rescue_pct \
               and pack_result.fill_rate_weight_pct < settings.min_fill_rescue_pct:
                add_candidates = choose_forwardable(forwardable, pack_result)
                improved = repack_with_additions(pack_result, add_candidates)
                forwardable = forwardable.remove(improved.newly_loaded_ids)
                replace(pack_result, improved)

        # 確定処理
        shipped_ids = collect_shipped_ids(day_ship_list)
        item_ledger.loc[shipped_ids, "status"] = "shipped"
        results.extend(day_ship_list)

    return results
より実務的にするなら、take_items_for_slot() の中でまず must_ship を destination / planned_container / lane で絞り込み、それでも空きが大きい枠だけ forwardable を足すようにします。逆に、forecast の低い future 情報は「未来が混むかもしれない」という警戒には使っても、当日の積載判断には混ぜすぎない方がよいです。rolling horizon 文献でも、不確実な先の情報を使いすぎると誤差伝播が起きやすいことが指摘されています。
KPIと可視化
コンテナごとの出力 KPI は、一つのスコアに潰さず、分解された判断材料として出す方が現場向きです。最新の 3D packing ベンチマークや産業向け packing 研究でも、単純な space utilization だけでなく、安定性、支持、荷重バランス、操作安全性を別々に見る方向が強まっています。したがって、最低限の KPI は「体積」「重量」「CG」「空きの偏り」「未積載」の 5 軸で持つべきです。
KPI	公式 / 定義	推奨表示
fill_rate_volume_pct	packed_volume / usable_volume * 100	体積充填率
fill_rate_weight_pct	total_weight / max_weight * 100	重量充填率
cg_x_mm	Σ m_i (x_i + l_i/2) / Σm_i	前後重心
cg_y_mm	Σ m_i (y_i + w_i/2) / Σm_i	左右重心
cg_z_mm	Σ m_i (z_i + h_i/2) / Σm_i	高さ重心
cg_dx_pct	(cg_x - L/2) / L * 100	前後偏差
cg_dy_pct	(cg_y - W/2) / W * 100	左右偏差
cg_z_ratio_pct	cg_z / H * 100	高重心比
unused_volume_total_m3	usable_volume - packed_volume	総空き体積
unused_volume_distribution	前/中/後 × 低/高 のゾーン別空き	空き偏在
unloaded_count	未積載件数	未積載
unloaded_volume_m3	未積載体積合計	未積載体積
重心アラートに関しては、一般的な「絶対規制値」はコンテナ単体では一律に決めにくいので、phase 1 は advisory threshold にするのが賢明です。文献は「重心を低く保つ」「バランスを保つ」必要性は強く支持していますが、実装でまず欲しいのは規制値の再現ではなく、危険傾向の可視化だからです。おすすめの初期閾値は次の通りです。
alert	推奨閾値	扱い
前後偏荷重 Warning	abs(cg_dx_pct) > 10%	advisory
前後偏荷重 Critical	abs(cg_dx_pct) > 20%	強警告
高重心 Warning	cg_z_ratio_pct > 45%	advisory
高重心 Critical	cg_z_ratio_pct > 55%	強警告
左右偏荷重 Advisory	abs(cg_dy_pct) > 10%	phase 1 は参考表示のみ
この設計だと、あなたが気にしている左右重心も計算はするが、最初から hard infeasibility にはしない、という折衷案が取れます。いすゞ側が「左右は考慮外でもよい」と言っていても、研究・開発としては cg_y を捨てる理由はありません。少なくとも 3D 画面に表示し、将来 soft penalty に上げられる形にしておくべきです。実務向け packing 研究でも weight distribution constraints は common in practice とされているため、フィールド UI では advisory 指標として持っておく価値があります。
空き体積は total だけでは足りません。unused volume distribution を front / middle / rear × low / high の 6 区画で出すと、「全体として 20% 空いている」のか、「前方下段に大穴がある」のかが区別できます。左右方向を hard に扱わない phase 1 では 3×1×2 の 6 分割で十分です。もし後で 2 列積載を精密に評価したくなったら、3×2×2 に拡張します。
可視化は、現場向けには 3D + 2D + timeline の三画面構成が最も伝わりやすいです。3D は最終姿勢、2D は作業順、timeline は「なぜ今日その荷物を使ったか」の説明責任を担います。研究ベンチマークでも、packing plan を可視化しながら構造安定性や運用安全性を評価する方向が強まっています。

テスト計画と既存コード統合
テストは、レイアウト品質、時間軸判断、データ健全性を別々に壊しにいくべきです。real-world 3D-BPP のベンチマークや instance generator でも、重量、カテゴリ親和性、優先順、負荷分散、物理実現性を分けてテストしています。したがって、2か月のサンプルデータは 1 本だけで済ませず、少なくとも「標準」「締切厳格」「重量ストレス」の 3 本を作るのが望ましいです。
